# 02 データモデル

画面が読む形(メタデータとレコード)と、それを PostgreSQL にどう置くかの案。
**いま動いているのはモックだけ**で、正は `frontend/src/mocks/fixtures/*.json`(DB の行と同じ形)と `frontend/src/api/types.ts`(型)。
PostgreSQL のスキーマは J-022 で確定する。§4 はそのための下書き。

## 1. 考え方

1. **定義もデータ。**テーブル(`objects`)・項目(`fields`)・ビュー(`views`)の定義をメタデータとして持ち、画面はそれを読んで描く(01 D-01)
2. **レコードは「DB の 1 行」そのまま。**列名は snake_case、ID は UUID、日付は `YYYY-MM-DD`、日時は ISO 8601(UTC)。画面は camelCase に直さない。変換の層を挟まないので、API の返り値をそのまま差し込める
3. **参照は ID で持ち、表示名はサーバが添える。**レコードには `account_id` だけが入り、一覧の応答に `references`(テーブル名 → ID → 表示名)が付く。SQL でいう JOIN を画面にやらせない
4. **業務ルールはサーバ側。**「完了にしたら完了日時を入れる」「フェーズを変えたら確度を既定値にする」は、画面ではなくサーバ(いまはモックの `applyRules`)が行う。画面・MCP・AI チャットのどこから書いても同じ結果になる

## 2. メタデータ

### objects(テーブルの定義)

| 列 | 意味 |
|---|---|
| `key` | テーブル名。URL(`/o/accounts`)と API のキーにも使う |
| `label` / `icon` / `color` | 表示名、lucide のアイコン名、色(タグと同じ 9 色) |
| `name_field` | レコードの表示名に使う列(取引先なら `name`、タスクなら `title`) |
| `subtitle_field` | 検索結果などで名前に添える列(任意) |
| `position` / `in_sidebar` | サイドバーの並びと、出すかどうか。出さないテーブル(活動)も、パネルの関連リスト・検索・URL からは開ける。環境設定のスイッチで変える(05 §11) |
| `completion` | チェックで完了にできるテーブルの設定(`field`・`done_value`・`open_value`・`completed_at_field`)。いまはタスクだけ |
| `timeline` | 活動(時系列の記録)のテーブルの印。`subject` / `type` / `date` / `body` に、件名・種別・日付・内容の列名。レコードのパネルには関連リストでなく時系列で出る(05 §9) |
| `system` | 初めから入っているテーブル(4 つ)。業務ルールやタスクの追加欄が前提にしているので、画面から削除できない |
| `fields` | 項目の定義(下) |

### fields(項目の定義)

| 型 | 中身 | 備考 |
|---|---|---|
| `text` `textarea` `email` `phone` `url` | 文字 | 検索の対象 |
| `richtext` | 書式付きの文字(太字・斜体・取り消し線・箇条書き・番号付き・リンク・見出し・引用) | 値は HTML。**描く前に許した要素だけを残す**(`lib/richtext.ts`。サーバも保存前に同じ規則で洗う)。検索と CSV は書式を落とした文字で。活動の「内容」 |
| `drive_files` | Google ドライブのファイル(複数) | 値は `DriveFile[]`(`id`・`name`・`mime_type`・`url`)の JSON 文字列(PostgreSQL では JSONB)。「新規」で「マイドライブ / CRM / テーブル名 / レコード名」のドキュメントを作り、「参照」でドライブから選ぶ(04 §8)。新規作成フォームには出ない(ドキュメントの名前にレコード名を使うため)。CSV は書き出しだけ |
| `number` `currency` `percent` | 数値 | `currency` は円。一覧の下に合計が出る |
| `date` `datetime` | 日付、日時 | `semantic: "deadline"` を付けると締め切りとして扱い、過ぎていてレコードが終わっていなければ注意色 |
| `select` | 選択肢 | `options` に `value`・`label`・`color`。カンバンの列になる。選択肢に `kind`(open / won / lost / done)と `probability` を持てる |
| `multi_select` | 複数選択(ラベル、タグ) | `options` は `select` と同じ。値は選んだ `value` の配列(JSON。PostgreSQL では JSONB)。サーバが重複を除き定義順に揃える。条件は「のどれかを含む / どれも含まない」(jsonb の `?|`)。カンバンでは分けられない |
| `checkbox` | 真偽 | |
| `relation` | 別テーブルへの参照(`target`) | 列 = `key`(例 `account_id`) |
| `polymorphic` | 複数テーブルのどれかへの参照(`targets`) | 列は 2 本(`columns.object` にテーブル名、`columns.id` に ID)。タスクの関連先 |
| `user` | 利用者への参照 | |

共通の属性: `required`、`readonly`(システムが埋める列)、`in_create_form`(新規作成フォームに出すか)、`placeholder`、
`max_length`(文字の列の桁数。超えたら 400)、`scale`(`number`・`percent` の小数の桁数。サーバがこの桁で丸める)、
`locked`(業務ルールが使う列。商談のフェーズと確度、タスクの優先度、活動の種別と元のタスク。テーブル設定から外せず、型も変えられない)、
`all_targets`(`polymorphic` で、全テーブルを指せる印。テーブルを足すと `targets` にも加わる。活動の関連先)。

### views(ビューの定義)

1 テーブルに何枚でも持てる。画面のタブはこの並び(`position`)。`pin` を付けるとサイドバーの「お気に入り」に出る(`show_count` で件数付き)。
**一覧とカンバンは画面から作れて、直せる**(2026-09-22。05 §10、API は 04 §2 の `/meta/views`)。レポートの部品(`widgets`)だけは、まだ JSON で定義する。削除は論理削除(戻せる)。

| 型 | `config` |
|---|---|
| `list` | `columns`(列と幅。幅は px で、見出しの右端をつまんで変える。05 §12)、`filter`、`sort` |
| `kanban` | `group_by`(選択肢の列)、`card_fields`、`sum_field`(列見出しの合計)、`hidden_groups`(出さない列。完了済みなど)、`filter`、`sort` |
| `report` | `widgets`。`stat`(数字 1 つ。`denominator_filter` で割合、`secondary` で補足、`tone: alert` で注意色)と、`bar` / `column`(`group_by`・`measure`・`color`・`order`・`limit`・`wide`) |

フィルタ・並び・集計の書き方は 04 §3〜§5。

## 3. テーブル(初回ローンチの 5 つ + 利用者)

全テーブル共通: `id`(UUID)、`created_at`、`updated_at`。以下は主な列。全量は `fixtures/objects.json`。

| テーブル | 主な列 |
|---|---|
| **accounts** 取引先 | `name`(必須)、`name_kana`、`type`(見込み客 / 顧客 / パートナー / その他)、`industry`、`phone`、`website`、`prefecture`、`address`、`employees`、`owner_id`、`description` |
| **contacts** 取引先責任者 | `name`(必須)、`name_kana`、`account_id`(任意。所属の無い人も持てる)、`department`、`title`、`email`、`phone`、`role`(決裁者 / 推進役 / 窓口 / 技術担当 / 経理 / その他)、`status`(関係: 新規 / やり取り中 / 定期フォロー / 休眠)、`last_contacted_on`、`owner_id`、`description` |
| **opportunities** 商談 | `name`(必須)、`account_id`(必須)、`primary_contact_id`、`stage`(見込み → ヒアリング → 提案 → 見積 → 交渉 → 受注 / 失注。選択肢に確度の既定値と open / won / lost)、`amount`、`probability`、`close_date`(締め切り)、`type`、`lead_source`、`next_step`、`owner_id`、`description` |
| **tasks** タスク | `title`(必須)、`status`(未着手 / 進行中 / 相手待ち / 完了)、`priority`(P1〜P4。色は Todoist と同じ赤・橙・青・灰)、`due_date`(締め切り)、`repeat`(繰り返し: 毎日 / 平日 / 毎週 / 隔週 / 毎月 / 毎年)、`repeat_from_completion`(完了した日から数える)、`repeat_of`(前回)、`labels`(複数選択)、`related_object` + `related_id`(関連先: 取引先か商談)、`contact_id`、`assignee_id`、`description`、`documents`(Google ドライブ)、`completed_at` |
| **activities** 活動(2026-09-22) | `subject`(件名。必須)、`type`(種別: 電話 / メール / 打ち合わせ / 訪問 / Web 会議 / メモ / その他)、`occurred_on`(日付。必須。空なら今日)、`related_object` + `related_id`(関連先: **全テーブル**)、`body`(内容。書式付き。`@` で他のレコードに言及できる)、`mentions`(サーバが `body` から写す、言及先の `テーブル名:ID` の一覧。PostgreSQL では `activity_mentions` の結合表)、`owner_id`(記録者)。**タスク(未完了の管理)と活動(起きたことの記録)は別のテーブルで、完了したタスクを活動に複製しない**(時系列 API が合成する。04 §9)。商談には `documents`(Google ドライブ)も足した |
| **users** 利用者 | `name`、`email`、`avatar_color`、`admin`(環境設定を触れる印。ロールは持たない。権限の設計は J-038)。サイドバーには出さない |

関連リスト(レコードのパネルの下半分)は定義しない。**メタデータから「このテーブルを参照している列」を探して自動で出す**(取引先を開くと、取引先責任者・商談・タスクが並ぶ)。テーブルが増えれば関連リストも増える。

### サーバ側の業務ルール(いまはモックの `applyRules`)

- `completion.field` を `done_value` にしたら `completed_at` に現在時刻。戻したら NULL
- **繰り返し(Todoist の型。2026-09-22)**: `repeat` が入ったタスクを完了にすると、その回は完了済みの行として残り(時系列に出る)、**次回のタスクをサーバが作る**(期限は元の期限から規則ぶん進める = Todoist の `every`。`repeat_from_completion` なら完了した日から = `every!`。件名・優先度・関連先・ラベルなどを写し、`repeat_of` に前回の ID)。**完了を戻したら、その回から自動で作った次回(まだ未着手のもの)を消す**。各回が行として残り `repeat_of` で繋がるので、履歴と「戻すと次回が消える」の両方が成り立つ。Todoist は 1 つのタスクの期限を進める作りだが、時系列に各回を出すために行を分けた(08 §4)
- 商談の `stage` を変えたら、`probability` をそのフェーズの既定値にする(同時に確度を指定したときは尊重)
- 作成時の既定値: 必須の選択肢は先頭の値、`user` 型は自分、タスクの優先度は P4、活動の日付は今日
- 活動の `body` を書いたら、その中の `@` の言及(`<span data-type="mention" data-id="テーブル名:ID">`)を `mentions` に写す。画面のどこから書いても同じ。**正は `body` で、`mentions` は検索のための導出値**(捨てて再計算できる)。向きは活動 → 言及先の一方向で、**言及された側のレコードには何も書かない**(複製もポインタも持たない。時系列は 04 §9 が引く)
- 完了したタスクを活動に複製する規則は**採らない**(2026-09-22 に一度作って取り下げた)。理由: 初めから完了していたデータ(種、Todoist からの移行分)に記録が無く、時系列に穴が空く。時系列は読むときにサーバが合成する(04 §9)
- 更新のたびに `updated_at`

## 4. PostgreSQL への置き方(下書き。J-022 で確定)

- 4 つのテーブルは**ふつうの実テーブル**にする(列に型と制約が付き、集計が素直な SQL で書ける)。`relation` は FK、`select` は `text` + メタデータでの検証(選択肢を変えるたびに ALTER TYPE しないため、enum 型は使わない)
- メタデータは `meta_objects` / `meta_fields` / `meta_views` の 3 表。`options` と `config` は JSONB
- `polymorphic` は FK を張れない。`related_object` は `meta_objects.key` への FK、`related_id` は書き込み時にアプリが検証する(関連先の組・targets の中・行がある)。**論理削除中は参照を保つ**(関連リストと時系列は削除済みを出さないだけ。元に戻せば関連も戻る)。掃除するのは完全に捨てるときだけ(08 §2)
- 検索は `pg_trgm`(規模が小さいので足りる)。ひらがな・カタカナ・全角半角の正規化は、検索用の列を 1 本持って吸収する。**文字の項目を外した・戻したときは、この列を全行作り直す**(外した項目の値で当たり続けないように。値は変えないので `updated_at` は動かさない)
- 削除は論理削除(`deleted_at`)。画面の「元に戻す」はこれを外すだけ(API は `POST …/restore`)
- ID は UUID v7(時系列順に並ぶ)

**画面から追加したテーブル(§5)のレコードも、実テーブルに置く**(2026-09-23 決定。Q-036)。

- テーブルを足す = `CREATE TABLE`、項目を足す = `ALTER TABLE … ADD COLUMN`。**`DROP` は使わない**(項目を外すのはメタデータで隠すだけ。§5 の「外した列の値は残す」「同じ列名で戻せば復活」がそのまま守られる)
- **Alembic は「初めからあるテーブル」(§3 の 5 つ + 利用者 + `meta_*`)だけに使う。**画面から足したテーブル・列は `meta_objects` / `meta_fields` を正として、アプリが実行時に DDL を流す。この二重管理を追えるように、**流した DDL の履歴表を持つ**(誰が・いつ・どの文を流したか。形は J-022 で決める)
- 採った理由: 型・NOT NULL・FK が DB 側で効き、集計・並び・`pg_trgm` の検索が素直な SQL になる。JSONB の 1 表にすると、この全部がアプリの責務に移る(比較は 08 §3 の 1)
- DDL を流す経路は 1 本に絞る(テーブル設定の保存 API だけ)。`meta_*` の更新と DDL は同じトランザクションで行い、片方だけが残らないようにする

## 5. 画面からのテーブル設定(2026-09-22。モックで実装済み)

テーブルと項目は、画面(05 §8)から足せて、直せる。API は 04 §6。振る舞いの正は `frontend/src/mocks/schema.ts`。

| 決まり | 理由 |
|---|---|
| **列名(`key`)は作成後に変えられない。**テーブル名も同じ。小文字の英字で始まり、英数字と `_`。`id`・`created_at`・`updated_at` は予約 | URL・API・CSV・ビューの定義が列名で指している。変えるなら移行が要る。表示名(`label`)はいつでも変えられる |
| 列名は画面が提案する(英数字の名前ならそこから、和文なら `field_1`・`table_1` の連番)。作成時だけ手で直せる | 和文はローマ字にできない。考えさせずに先へ進める |
| **作成した項目の型は変えられない** | 値の変換が要る。要るなら、新しい項目を足して移す |
| 新しいテーブルの**先頭の項目がレコードの表示名**(`name_field`)。文字(1 行)・必須に固定。`created_at`・`updated_at` はサーバが足す | どのテーブルにも、一覧とリンクに出す名前が要る |
| **項目を外しても、列の値は消さない。**外した項目の定義はサーバが保管し、**同じ列名で戻せば元の定義(型・参照先)が復活する**(違う型では戻せない)。外した項目の値では検索(`q`・横断検索)に当たらない(戻せばまた当たる)。テーブルの削除も論理削除で、レコードとビューは残る(`restore` で戻る)。**削除済みと同じ列名のテーブルは作れない**(戻すか別名に)。初めから入っている 5 つ(`system`)は削除できない | 画面は確認を挟まず「元に戻す」で守る(05 §5)。戻せるためには、消してはいけない。列の値を別の型として読ませない |
| 無くなった項目やテーブルを指す定義(ビューの列・並び・**条件**、カンバンの分け方、レポートの部品、参照の項目)は、**保存してある形を壊さず、`GET /meta` で返すときに外す**。条件を外すと絞り込みが緩んで表示が広がる(それでも 400 で止まるより良い)。全量置換(`PUT`)の本文に、隠れているだけの項目・列が無くても、サーバは外さない | 「元に戻す」が、前の定義をもう一度保存するだけで済む。参照先を戻せば、隠れていた項目も戻る |
| 表示名の項目、`readonly`、`locked`、`completion` が使う列、`timeline` が使う列、`polymorphic` は外せない。`completion` の `done` / `open` の選択肢は消せない | 業務ルールと画面の機能が前提にしている |
| ビューを画面から編集する機能が無いあいだは、サーバが面倒を見る: 一覧が無ければ作る。**足した項目は先頭の一覧の列に加える。**カンバンが無く選択肢の項目があれば、その項目で分けるカンバンを作る | 足した項目がどこにも見えない、を避ける |
| 画面から足せる型は `polymorphic` 以外の全部。`relation` の参照先は作成時に選び、あとから変えられない | |

値の検証(必須・桁数・選択肢にあるか・小数の丸め)は書き込みの経路(`insert` / `update`)で行う。画面・取り込み・将来の MCP のどこから書いても同じ結果になる。

## 6. モックのデータ

- `frontend/src/mocks/fixtures/` に、メタデータ(`objects.json`・`views.json`。手で書く)とレコード(`accounts.json` ほか。`npm run fixtures` で生成)を置く。会社・人物は架空、メールは `example.jp`、電話は実在しない局番
- レコードの日付は生成時の基準日で書かれており、モックが読み込むときに「今日」基準へずらす。いつ開いても、今日のタスクと今月の商談がある
- 画面での変更は localStorage に残る(レコードは `works.mock.tables.v1`、テーブル設定は `works.mock.schema.v1`)。利用者メニューの「モックのデータを初期化」で両方戻せる
