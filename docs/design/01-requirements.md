# 01 要件と決定

Works(このリポジトリで作る自作 CRM)が何であり、何を決めたか。決定には理由を付ける。
決定を変えるときはこの文書を更新し、`backlog/QUESTIONS.md` の該当項目にポインタを残す。

## 1. 目的と性格

- **あり物を使わず、完全に AI で自作する CRM。**GAS・NocoDB・Twenty などの既製品を試したうえで、挑戦として自作に切り替えた(2026-09-21、本人の決定。それまでの経緯は README)
- これまでの顧客管理(Notion・Google コンタクト・退避済みの連絡先台帳)をこの仕組みに置き換え、**Todoist も廃止する**のが到達点
- 命は 3 つ。**きれいで「イケてる」画面、使いやすさ、サクサク動く軽快さ。**機能の数より、この 3 つを落とさないことを優先する
- 利用者は当面 1 名(本人)。画面とデータの作りは複数人を妨げないが、複数人のための機能(権限の細分化、招待)は作らない

## 2. 初回ローンチのスコープ

| 領域 | 中身 |
|---|---|
| テーブル | **取引先・取引先責任者・商談・タスク**の 4 つ |
| タスク | Salesforce の Task と同じく、各テーブルのレコードに紐づく(関連先 + 取引先責任者)。何にも紐づかない個人のタスクも持てる(Todoist の代わり) |
| ビュー | **一覧・カンバン・レポート(グラフと集計)。**テーブルを開いた画面の中で、タブで切り替える |
| 画面の骨格 | Notion / Twenty 風。左のサイドバーに DB のテーブルが並ぶ |
| 操作 | Todoist の気持ちよさ。完了のチェックで即座に一覧から消える。`Q` でタスク追加、`/` で検索。マウスなしで一周できる |
| ログイン | **ログインとセッションはアプリ自身がすべて持つ。手前に門(Cloudflare Access)は置かない**(2026-10-01。D-14): メールアドレスとパスワード + 2 段階認証(TOTP)、または Google でログイン。スマホのアプリと AI のエージェント(MCP)も、同じ公開 URL に直に届く。本番で Access を外すのは J-055 |

ローンチ後に回したもの(`backlog/JOBS.md`): MCP サーバ、サイドバーの AI チャット、ドキュメントの採番・命名ルールの整理。
**テーブルを画面から追加・設定する機能(Airtable / kintone 風)は、2026-09-22 に本人の指示で前倒しし、モックに入れた**(画面は 05 §8、契約は 04 §6、決まりは 02 §5)。バックエンド側は J-033。

## 3. 決定

### D-01 画面はメタデータで描く

- テーブル・項目・ビューの定義を**データ**として持ち(02 §1)、画面はそれを読んで描く。サイドバーに並ぶのは DB のテーブルそのもの
- 理由: ローンチ後に「テーブルを画面から追加する」をやるとき、画面を作り直さずに済む。取引先専用・商談専用の画面を 4 枚作ると、5 枚目を足すたびにコードが要る
- 帰結: 画面のコードにテーブル名・項目名を書かない。例外は「タスクの追加欄(Q)」だけで、それも `completion` を持つテーブルをメタデータから探している

### D-02 画面とバックエンドは JSON の契約で分ける

- 画面は SPA、バックエンドは Python の JSON API。契約は 04 と `frontend/src/api/types.ts`(型が正)
- 画面は `ApiClient` という窓口 1 つだけを通してデータに触る。実装は **mock**(ブラウザ内の擬似 DB)と **http**(本物の API)の 2 つで、環境変数 1 つで切り替わる(03 §3)
- 理由: バックエンドが無いうちから画面を完成させられ、できたら差し替えるだけで済む。モックのデータは DB の行と同じ形(列名は snake_case、ID は UUID、参照は ID)なので、プログラムの返り値をそのまま差し込める

### D-03 画面のスタック: Vite + React + TypeScript + Tailwind CSS v4

- 軽快さの要は楽観更新とキーボード操作で、どちらも SPA が向く。React は部品(ドラッグ&ドロップ、データ取得のキャッシュ)が最も揃っている
- 見た目は全面的に Tailwind CSS。色・文字・影・動きはトークンとして `frontend/src/styles/index.css` に定義する(05 §4)
- 採用したライブラリと、非推奨でないことの確認結果は 03 §9

### D-04 バックエンドは Python、DB は PostgreSQL。フレームワークは未決

- 言語は Python(本人の決定)。フレームワークは議論して決める → **Q-034**。比較と推奨は 03 §4
- DB は PostgreSQL 18。Compose に定義だけ置いてある(バックエンドを足すまで起動しない)

### D-05 Docker Compose で動かす。Docker は WSL2 の中のものを使う

- いまは Surface(WSL2)で動かすが、いざというとき AWS などへ引っ越せるよう、最初から Docker で組む。状態を持つのは PostgreSQL だけにし、画面と API のコンテナは無状態に保つ
- **Windows 側の Docker Desktop は使わない。**WSL2 の Ubuntu に入れた Docker Engine を使う(`docker context` の `default`)

### D-06 公開は Cloudflare Tunnel、`works.sanei-clover.com`(門の Cloudflare Access は外す)

- Surface から Cloudflare へ外向きに張るだけで、受信ポートを開けない。DNS は Cloudflare(共通ルール)
- 2026-09-21〜: 前段に Cloudflare Access を置き、本人のメールアドレスだけを通した。セッションは 30 日(短いと PIN の往復が日常の負担になる。Twenty のときはそれが理由で Access を外した)
- アプリ自身のログインは **Access を信頼する**形だった(2026-09-24。J-023)。Access の JWT のメールアドレスで利用者を決め、アプリはログイン画面を出さない。03 §5
- 2026-10-01、ログインとセッションはアプリ自身が持つ形に変えた(D-14)。同日、いったん「Access は門として残す」と見直したが、**同じ日のうちに、Access を外す(素通しにする)と決め直した**(本人。D-14 の 2 度目の見直し)。本番で外すのは J-055(手順は 06 §3)

### D-07 タスクは「関連先」と「取引先責任者」の 2 本で紐づく

- 関連先 = 取引先か商談のどちらか 1 件(`related_object` + `related_id`。Salesforce の WhatId)。取引先責任者 = 人(`contact_id`。同 WhoId)
- どちらも空でよい。空のタスクが Todoist の代わりの個人タスク
- 関連先になれるテーブルはメタデータ(`targets`)で決まるので、テーブルが増えても同じ仕組みで紐づく

### D-08 操作は Todoist に寄せる

- 完了はチェック 1 回。押した瞬間にチェックが入り、行が抜け、「元に戻す」が出る。確認ダイアログは出さない(削除も同じ。取り消せることで守る)
- 追加は `Q`。件名に「明日」「金曜」「9/30」「p1」と書けば期限と優先度として読む。レコードを開いた状態で `Q` を押すと、そのレコードが関連先に入る
- キーの一覧は 05 §3。日本語入力の変換中は、どのショートカットも反応させない

### D-09 デザインは Anthropic 公式の skill に従って決める

- 画面全体は `frontend-design`(claude-plugins-official)、グラフは `dataviz` の手順で決めた。配色・書体・動きの決めごとと、その理由は 05 §4
- グラフの色は目で選ばず、`dataviz` の検証スクリプトを通した値だけを使う

### D-10 データの置き場と個人情報

- モックの間、データはブラウザの中(localStorage)だけにある。フィクスチャの会社・人物はすべて架空
- **このリポジトリは公開。個人情報は Git に入れない。**実データの退避先は `~/backups/perfect-crm/`(07)

### D-11 AI の入口は 2 つ。どちらも同じコマンド層を通す(ローンチ後)

- **外から**: MCP サーバを公開し、Claude Code や Codex からレコードを読み書きする(J-028)
- **中から**: サイドバーをチャット欄に切り替えられるようにする(Notion AI / Twenty 風。J-029)。LLM は **Amazon Bedrock でも、個人の Claude API キーでも使えるように差し替え可能にする**(本人の前提。設計は 03 §7)
- どちらも、画面と同じ書き込み経路(検証・業務ルール・記録)を通す。AI 専用の抜け道を作らない

### D-12 通知は Slack の Incoming Webhook。llm-wiki の稼働通知と同じ Slack アプリを流用する(2026-09-30)

- 本人の指示: 「Web フォームから登録がなされたとき、自社の Slack に飛ばす。Slack アプリは SANEi CLOVER Inc. の Slack から出す」(leadcast-sales の Slack アプリは LEADCAST Inc. の Slack から出している)
- 新しいアプリは作らず、SANEi CLOVER の Slack にある llm-wiki の稼働通知のアプリを流用する(同日、本人の判断)。共有するので、Works からはアプリを外さない
- 権限は `incoming-webhook` だけ。チャンネルは Slack の許可の画面で選ぶ(04 §14)。Q-027(通知の経路。2026-09-19 に「要るときに決める」)の答え
- 当初は「Web フォームの登録を 1 チャンネルへ」だけだった。同日、何をいつ知らせるかをワークフロー(D-13)で決める形に替え、チャンネルは複数持てるようにした

### D-13 ワークフロー: 「きっかけ」と「アクション」の組で、知らせることを汎用に決める(2026-09-30)

- 本人の指示: 「リード登録時に Slack 通知させるトリガーを、リードのみならず汎用的に使えるように」。名前は**ワークフロー**、将来の拡張もできる画面と作りに
- 1 つのワークフロー = **きっかけ 1 つ**(どのテーブルで・いつ・どの条件で・どこからの書き込みで)+ **アクションの並び**。「いつ」は「作成されたとき」と「条件を満たしたとき」(満たしていなかったものが満たした瞬間に 1 回)の 2 つで始める。時刻を起点にするもの(期日の前日など)と「特定の項目が変わったとき」は、要るときに足す
- アクションはいまは「Slack に知らせる」だけで、**ワークフロー(のアクション)ごとにチャンネルを選ぶ**。メール・レコードの作成などは、アクションの種類を足して載せる(`app/workflows/actions/`、画面は `lib/workflow.ts` の `ACTION_KINDS`)
- 送った・送れなかったは、専用の管理表(**実行記録** `workflow_runs`)に持つ(本人の提案)。送信待ちの台帳を兼ね、書き込みと同じトランザクションで入れ、確定したものだけを送り係が送る。Slack が止まっていても間を空けて送り直す
- これまでの「Web フォームから登録があったら知らせる」は、同じ動きのワークフローに移して、仕組みを 1 つにした(マイグレーション 0008)
- 条件はビューのフィルターと同じ(意味も同じ SQL)。CSV の取り込みは、既定では動かさない(100 件入れると 100 通届く)
- 設計: API 04 §15、データ 02 §7、送り係 03 §11、画面 05 §14

### D-14 ログインはアプリ自身が持つ: メールアドレスとパスワード(+ TOTP)、Google でログイン(2026-10-01)

- 本人の決定: 「ログインは Access ではなく、自前で持つ。ID・パスワード方式と Google のシングルサインオンが使える前提で」
- 同日の見直し(本人): いったん Access は門として残すことにした。「Surface で稼働させている以上、Access は必要。そのうえで、ログイン機能とセッション管理はシステム側に持たせる」。アプリや部品に未知の穴が見つかっても、許可した人以外は攻撃を始められない、という理由だった。スマホのアプリは Cloudflare WARP(Cloudflare One Agent)で門を通る案だった
- **同日の 2 度目の見直し(本人): Access を素通りにし、ログインとセッション管理は全面的にシステム側に持たせる。スマホのアプリや AI のエージェントからのリクエストも届くようにする。**門があると、ブラウザ以外(Android アプリ・Claude Code・Codex など)は、WARP やサービストークンのヘッダを持たないと届かない。門を外せば、どれも公開 URL に直に届き、Works の OAuth とトークンだけで済む
- **引き受けること(2 度目の見直しで)**: ログインの前の口(ログイン・MCP の登録と許可の依頼・Web フォームの受け口・Google と Slack の戻り)に、インターネットのだれからでも届く。アプリや部品にログインの前で効く穴が見つかれば、そのまま攻撃を受ける(門が防いでいたもの)。守りは 03 §5「門を置かずに守る」。Surface は社内 LAN の PC で、api のコンテナが乗っ取られたときの被害は大きい(api のコンテナは読み取り専用で、権限をすべて落としてある。`docker-compose.yml`)
- 同日の追加の決定(本人): **パスワードで入るときは 2 段階認証(TOTP)を必須にする**(Q-048)。Google で入れるのが Workspace のアカウントだけなのは、それでよい。既定値(ブラウザのセッション 30 日、メールでの再設定を持たない、Android アプリに許可のカードを出さない)も了承
- 理由: ①**Android のネイティブアプリ(D-15)には、Access の JWT だけでは利用者を決められない**(Access のログインはブラウザの Cookie で成り立つ)。アプリはアプリ自身のログイン(OAuth)で誰かを示す ②**引っ越しで作り直さずに済む**(D-05。Access を信頼する形は Cloudflare の外では成り立たなかった。06 §6)③画面・アプリ・MCP の許可が、同じログインに揃う ④2 段階認証・端末ごとのログアウト・パスワードを変えたときの切断など、Access では細かく扱えないことをアプリが持てる
- ログイン ID はメールアドレス(`users.email`)。Google は、Works に登録してあるメールアドレスの Google アカウントだけが入れる。**利用者が勝手に増えることはない**(足すのは管理者。名乗り出て登録する口は作らない)
- Google の OAuth クライアントはドライブと同じもの(J-040)で、対象は「内部」。だから **Google で入れるのは Workspace(sanei-clover.com)のアカウントだけ**(本人が了承)。個人の Gmail で使う人が出たら考え直す
- アプリの守り: パスワードの長さとハッシュ、**パスワードで入るときの 2 段階認証(TOTP)**、続けて失敗したときの待ち、セッションの期限、書き込みの `Origin` の確かめ。門が無いので、これが守りの本体になる。だれでも叩ける口には、間引きと、たまる行の上限と、本文の大きさの上限を持つ(03 §5)。Google で入るときの 2 段目は Google に任せる(Workspace の管理コンソールで 2 段階認証を必須にしておく)
- ブラウザでログインするのは月に 1 回、Works(パスワード + 6 桁)だけ(門があった頃は、Access と Works の 2 回だった)
- 設計: 仕組み 03 §5、口 04 §16、表 02 §8、画面 05 §15、外し方と外から使う口 06 §3・§7。作業は J-053(パスワードと TOTP。済み)→ J-055(本番の切り替えと、Access を外す)→ J-054(Google)

## 4. 非機能要件

- **軽快さ**: 一覧・パネル・タブの切り替えは体感で即時。更新は楽観的に反映する。最初に読む JS は 120KB(gzip)程度に抑え、カンバンとレポートは遅延読み込み
- **きれいさ**: 明暗の両テーマ。和文は OS の UD 系ゴシック、欧文と数字は Figtree。太さは 2 段階だけ(05 §4)
- **キーボード**: 主要な操作はすべてキーで届く。フォーカスの輪郭を消さない
- **スマホ**: 同じ画面がそのまま使える(サイドバーは引き出し、パネルは全画面)
- **ログインの守り**: パスワードで入るときは 2 段階認証(TOTP)も要る。パスワードは 15 文字以上で、Argon2id で保存する。続けて失敗したら待たせる。ブラウザのセッションは 30 日で切れる。Google で入れるのは Workspace のアカウントだけ。手前に門を置かないので、ログインの前の口はアプリが守る(D-14、03 §5)
- **日本語**: 検索はひらがな・カタカナ・全角半角を区別しない。金額は円、日付は「今日・明日・9月30日(水)」
