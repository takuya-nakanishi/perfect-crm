# 01 要件と決定

perfect-crm が何であり、何を決めたか。決定には理由を付ける。決定を変えるときはこの文書を更新し、`backlog/QUESTIONS.md` の該当項目にポインタを残す。

## 1. 目的と性格

- 顧客管理(CRM)・案件管理(SFA)・プロジェクト/タスク管理を一つにした業務システム
- **自社で使い、他社にも売る。**自社が最初のユーザー。自社の都合で入れたハードコードはそのまま製品の欠陥になるので、自社固有の値は設定かデータに出す
- **AI と密結合。**人の判断を軸に画面から入力する従来型の導線を主導線にしない。入力は AI エージェント(Claude Code、Codex、claude.ai 等)が MCP 経由で行い、人は画面で閲覧し台帳を直す。ただし画面からの入力も従来通りできる
- 正規化された顧客データは**この DB が正**。Notion・Google コンタクト・Todoist に散っている現状を置き換える

## 2. 機能要件

| 領域 | # | エンティティ | 要点 |
|---|---|---|---|

| 顧客管理 | 2 | 担当者 | 人。企業と多対多、主所属を 1 つ持つ。所属ごとに部署・役職・在籍期間 |
| 案件管理 | 3 | リード | 台帳未登録の生データ(問い合わせフォーム等)。変換時に企業+担当者+案件を生成し、重複を判定 |
| 案件管理 | 4 | 案件 | 受注に向けた管理。ステージは組織ごとに設定可能、パイプラインは単一。受注でプロジェクトへ変換可能 |
| プロジェクト管理 | 5 | プロジェクト | 受注単位・開発単位。案件なしの社内プロジェクトも可 |

| 横断 | 7 | 活動 | メモ・通話・打合せ・メール・システム変更を時系列に積む。「日々の活動を記録する」の受け皿。何にでも関連づく |
| 横断 | 8 | カスタム項目 | 全エンティティ。文字・数値・日付・選択・複数選択・関連・URL |
| 横断 | 9 | ビュー | サイドバーにエンティティ。一覧・詳細(タイムライン付き)・カンバン・今日のタスク |
| 横断 | 10 | MCP | サーバとして公開。検索・参照・記録・重複候補・タスク操作。企業の全文脈を Markdown で返す(エージェント側の ingest 用) |

## 3. 決定

### D-01 配布形態: セルフホストも SaaS も、同じ Docker イメージ

- 自社は Surface(WSL2)上の Docker で動かす。将来は SaaS としても提供できるようにし、サーバの引っ越しを容易にする
- 帰結: **マルチテナントは v1 から。**全テーブルに `organization_id`、PostgreSQL の RLS で強制。自社インスタンスでは組織が 1 つあるだけ。後から入れると全クエリの書き換えになる
- 帰結: アプリコンテナは無状態。状態は PostgreSQL と S3 互換ストレージだけ。クラウド固有サービスをコアに入れない
- 「拡張性」は規模と機能の両方(Q-017)。v1 はカスタム項目と MCP、Webhook は v2、カスタムオブジェクトは要望が出てから

### D-02 AI は外に住む

- CRM 自身は LLM を呼ばない。API キー・費用・プロンプトを製品に持たない。顧客は自分の Claude Code / claude.ai を持ち込む
- 「AI 密結合」の質は **MCP ツールの粒度と説明文**で決まる。CRUD だけでなく業務語彙のツール(`log_activity`、`get_context`、`find_duplicates`、`move_deal_stage`)を持つ
- 将来、Notion AI のような内蔵 AI を足す場合も、同じコマンド層を中から呼ぶだけ

### D-03 UI と MCP は同じコマンド層の 2 つのクライアント

- 全操作をコマンド(書き込み)とクエリ(読み取り)として `packages/core` に定義。HTTP API も MCP も薄い皮
- 入力は主にエージェントから。画面は閲覧と台帳の修正が主だが、従来通りの CRUD も持つ
- **スマホでも用途を制限しない。**全機能をレスポンシブで(Todoist の代わりにもなるため)

### D-04 AI は確認なしに書ける。CRM は 4 つで守る

- 確認はエージェント側(Claude Code の許可ダイアログ等)で行われる。CRM に承認キューは作らない
- CRM 側の守り: ①検証(型・必須)②**重複候補の返却**(黙って新規作成しない)③監査ログ(誰が・どのエージェントが・何を根拠に)④リビジョン(元に戻せる)

### D-05 チャネルは当面 Gmail のみ。受信はエージェントが担う

- CRM が持つ Google scope は `openid email profile` + `drive.file` + `gmail.send` の 3 つ。restricted scope を持たない(区分の確認は Q-022)
- 受信メールの記録は、エージェントが Gmail MCP で読み、perfect-crm の `log_activity` に書く。CRM に読み取り scope は要らない。製品としての OAuth 審査が軽くなる
- LINE・WhatsApp・電話は API 連携しない。理由: 個人 LINE / 個人 WhatsApp は API で取れず(公式アカウント / Business Platform の会話のみ)、電話はクラウド電話への乗り換えが前提になる

### D-06 タスクは「主所属」+「関連リンク」

- `project_id`(任意)+ `record_links` で企業・担当者・案件などに関連づける
- 全エンティティを `records`(supertype)に登録し、リンクに FK を効かせる(02 §1)

### D-07 カスタム項目は全エンティティ、JSONB+定義テーブル

- 定義は組織スコープ。値は各エンティティの `custom` 列(JSONB)。規模が小さいので検索・並び替えは GIN と式インデックスで足りる

### D-08 Google のファイルは利用者のマイドライブに、ID で保持。1 レコードに複数

- 1 レコードに複数のファイルを持てる。作れるのは Google ドキュメント・スプレッドシート・スライド。Google ドライブにある既存ファイルもリンクできる(Q-025)
- 作成先は `マイドライブ/PerfectCRM/{テーブル名}/{レコード名}/`。レコードごとにフォルダを切り、その中にファイルを作る(複数持つため、人間の指定 `{テーブル名}/{レコード名}` を 1 段深くした)。ファイル名の既定は `{種類} {日付}`(例 `議事録 2026-09-19`)
- ファイル ID とフォルダ ID を DB に持つ。名前・パスで探さない(`drive.file` では自分が作ったものしか見えず、手で作った同名フォルダは見えない)。利用者が Drive 側で改名・移動してもリンクは切れない。レコード改名にファイル名は追従させない
- 既存ファイルのリンクは Google Picker で選ぶ(`drive.file` の範囲で、利用者が選んだファイルにアプリがアクセスできる)か、URL を貼る(メタデータ無し)。**`drive.readonly` は足さない**(scope の不変条件)
- テンプレートは CRM 側に持ち、作成時に変換アップロードする(ドキュメント: HTML、スプレッドシート: CSV、スライド: PPTX)。Drive 上のテンプレートを `files.copy` する方式は採らない(`drive.file` では利用者ごとにアクセス権が要り、組織共通にできない)
- 作成者以外に見えないので、作成時に共有を付ける。共有先は組織の設定(`document_sharing`)で、既定はメンバー個別。ドメイン全体への共有は、同一 Google ドメインに複数の組織がある場合に他組織へ見え、別ドメインのメンバーには見えないので既定にしない。離職時に消えるリスクは承知の上(共有ドライブでないと避けられない)
- `{テーブル名}` は日本語表示名(企業・担当者・リード・案件・プロジェクト・タスク)

### D-09 スタック: TypeScript 端から端(確定)。個別のライブラリは候補

確定は「TypeScript 端から端、PostgreSQL、Docker」。以下のライブラリは候補で、**J-001 で一次資料を確認し、結果を 03 §9 に書いてから確定する**。

- pnpm workspaces。`packages/core`(ドメイン)/ `apps/server`(Hono)/ `apps/web`(Vite + React)
- PostgreSQL 18 + Drizzle、Better Auth、`@modelcontextprotocol/sdk`、pg-boss(必要になったら)、`pg_trgm`
- Next.js 一枚にしない理由: MCP の長時間接続とバックグラウンド処理を Route Handler に載せたくない、Docker セルフホストが重い、Vercel 寄りの設計に引っ張られる。認証済みアプリなので SSR の利点も薄い
- **採用前に各ライブラリが非推奨でないことを一次資料で確認する**(J-001)。Lucia はライブラリとして deprecated なので候補から外した

### D-10 稼働: Surface で始め、2 人目の前に常時稼働へ

- 利用者は当面 1 名、2〜3 名を見越す。1 名の間は Surface のスリープ・再起動で止まってよい(Q-013)
- 2 人目が使い始める前に、本番を常時稼働のホストへ移す(J-009)。同じ Compose が動く場所なら何でもよい

### D-11 移行元: Notion + Google コンタクト(顧客)、Todoist(プロジェクト・タスク)

- 合計 1,000 レコード程度、月の活動 100 件程度。規模の問題は無い
- 移行は `packages/core` のコマンドを直接呼ぶスクリプトで行い、重複ガードを効かせる(05)

## 4. 非機能要件

- 軽快さ: 一覧・詳細の表示は体感即時。規模が小さいので DB 側の工夫は不要、UI 側の設計(楽観更新・キーボード主導・コマンドパレット)で決まる
- レスポンシブ: スマホで全機能
- 日本語: 表示・フリガナ・前株/後株の正規化・法人番号。i18n は文字列を外に出す程度。JST・JPY
- 参照デザイン: Attio / Linear の方向
- 通知: v1 では設計しない(Q-027)。経路は要るときに決める

## 5. 制約(全リポジトリ共通ルール由来)

- DNS は Cloudflare。公開経路は Cloudflare Tunnel
- 非推奨ツールを使わない。採用前に確認
- 問い/作業は `backlog/`。設計の正はここ
- 文章は日本語

## 6. 段階

| 段階 | 内容 |
|---|---|
| v1 | 全エンティティ(企業・担当者・リード・案件・プロジェクト・タスク・活動)+ コマンド層 + MCP(API トークン)+ Google ログイン + 一覧/詳細/タイムライン/今日のタスク + `organization_id`+RLS + 移行。Claude Code から入力を始める |
| v2 | Gmail 送信・Docs 作成・カンバン・リード受け口(Webhook)・外向き Webhook・MCP の OAuth(同僚が claude.ai から使うため) |
| v3 | 製品化 — SaaS モード(自己登録・招待)、Google OAuth 審査、課金 |
| v4 | 内蔵 AI(Notion AI 型)、必要なら受信同期 |

v1 にタスク/プロジェクトを含めるのは Todoist を置き換えるため(D-11)。Todoist の機能のどこまでが v1 に要るかは未決(Q-018)。
