# 08 詳細設計に向けた棚卸し(2026-09-22)

モックの画面が一段落し、本人が「このデザインから DB とサーバの詳細設計を起こす」と決めた時点の棚卸し。
**観点は 3 つ**: ①機能間の矛盾 ②詳細設計で難しい・決めないと進めない箇所 ③backlog の問いと作業への拡張性。
(§1 の 15 だけは 2026-09-23 に足した。ほかは 2026-09-22 の棚卸し。)Codex(CLI、read-only)に未コミットの差分・設計文書・このセッションの人間の発言・Claude の説明(申告)を渡して独立レビューを取り、17 件の指摘を全部自分で確かめた。**事実誤認は無かった。**直せるものはその場で直し、決めごとは各文書へ落とし、判断が要るものは問い(Q-044・Q-045)にした。

## 3. 詳細設計で難しい・決めないと進めない箇所

1. **Q-036(実テーブルか JSONB か)が全部の入口 → 2026-09-23 に「実テーブル」で決着**(02 §4)。以下は決める前の比較で、根拠として残す。モックで固めた決まり(列名と型は不変、外した項目の値は残す、同じ列名で戻せば復活、論理削除)は、実テーブルなら「列は落とさず、メタデータで隠す」、JSONB なら「鍵を消さない」で、どちらでも満たせる。**実テーブルを勧める**(集計・並び・検索が素直。DDL は `ALTER TABLE ADD COLUMN` だけで、DROP は使わない)。マイグレーション(Alembic)は「初めからあるテーブル」だけに使い、画面から足したテーブル・列は `meta_*` を正としてアプリが DDL を流す。この二重管理をどう記録するか(DDL の履歴表)を J-022 で決める
2. **フィルタ・並び・集計の SQL 化**(J-021・J-024)。画面の `lib/filter.ts` と同じ意味に揃える: マクロの解決(§2 の 16)、選択肢の定義順(`CASE` か順序表)、参照の表示名順(`JOIN`)、`limit: 0` は `COUNT` だけ、日付の区間は `generate_series` で空の区間も返す、`weight_field` は `SUM(v * w / 100)`。**真理値表を J-021 の受け入れ条件にする**
3. **検索**: 文字の列に加えて richtext(書式を落とした文字)も対象。正規化(ひらがな・カタカナ・全角半角)した生成列に `pg_trgm`。richtext の洗浄は Python 側で同じ許可表(`nh3` などの現行のライブラリ。`bleach` は非推奨なので使わない)
4. **polymorphic(関連先)**: FK を張れないので、書き込み時の検証(§1 の 7)と、完全に捨てるときの掃除で守る。時系列 API(04 §9)は活動・言及・完了したタスクの 3 つの `UNION` — 言及は `activity_mentions` 表で引く
5. **論理削除**(`deleted_at`)を、レコード・テーブル・ビューの 3 段で持つ。**全部の読み取りが `deleted_at IS NULL` を挟む**ので、ビューかポリシーで一括に
6. **Web フォームの受け口**: 認証なし・間引き・bot 避け・303 と、Access の外への経路(Q-044)
7. **MCP**: トークンのハッシュ保存と最終利用の記録(J-039)、`/mcp` の経路(Q-044)、MCP サーバ本体(J-028)は同じプロセスに載せる。トークンは利用者ごとなのに発行が管理者だけ → 一般の利用者が自分の Claude を繋ぐ導線が無い。**J-038 で決める**(自分の分は自分で発行、を勧める)
8. **Google ドライブ**(J-035): 利用者ごとの OAuth の refresh token をサーバが持つ。Access の IdP(Google Workspace)とは別の同意になる
9. **移行**(J-026): 完了日時の尊重(§1 の 10)、CSV の ID 指定(§1 の 14)で通る。Todoist の完了履歴は活動に複製しないので、タスクとして取り込めば時系列に出る
10. **複数利用者**(J-038): メタデータ(テーブル・ビュー・お気に入り・サイドバーの並び)が全部ワークスペース共通。個人ごとに持つもの(お気に入り、サイドバーの並び、個人ビュー)を分ける設計が要る。§1 の 9 のリビジョン検査も
