# 05 移行

## 1. 移行元

| 元 | 行き先 | 取り方 |
|---|---|---|
| Notion「プロスペクト」 | 担当者 + 企業(名寄せで新規に起こす)+ リード | Notion API(MCP あり) |
| Notion「案件-プロジェクト」 | 案件 + プロジェクト(Q-028 で分け方を決める) | 同上 |
| Notion「活動の記録」 | 活動 | 同上。本文は Markdown で入る |
| Google コンタクト | 担当者 | People API か CSV。Notion と重複するので名寄せ |
| Todoist | プロジェクト・セクション・タスク・ラベル、コメント → 活動 | Todoist API(MCP あり) |

規模: 合計 1,000 レコード程度。

## 2. Notion の実構造(2026-09-19 に確認)

3 つの DB が相互にリレーションで結ばれている。ページ「🏄🏻 【人脈】リード＆仲間」の配下。

### プロスペクト(人)

`名前`(title)、`Furigana`、`企業名`(**text。企業 DB は無い**)、`部署名`、`役職名`、`メール1` `メール2`、`電話1` `電話2`、`住所`、`誕生日`、`出身地`、`TOBE`(multi_select: BP / 友達 / リード / セフレ)、`メモタグ`(multi_select: Web問合せ / 師匠 / コンサル・Engineer / 転職・SES Agent / 営業 / SES可 / 専門家-士業 / 取引先 / 社長)、`最終タッチ日`、`次のアクション`、`特記事項`、`SF取引先ID` `SF取引先責任者ID`(Salesforce の残骸)、案件と活動へのリレーション。

### 案件-プロジェクト

`プロジェクト名`(title)、`ステータス`(status: 1-新規 / 2-案件理解/見積 / 5-受注 / 6-完了。3・4 は欠番)、`客先担当者`(プロスペクトへ、limit 1)、`請求先担当者`(同、limit 1)、`担当者`(person)、`決済条件`(1-月末-翌月末 / 2-月末-翌々月15日)、`完了/予定日`、`次のアクション`、`案件NO`(formula)、`【計算用】NO`(auto_increment)、活動へのリレーション。**金額の項目は無い。**

### 活動の記録

`件名`(title)、`日付`、`タグ`(multi_select: ビジネスアイデア / KPI交流 / 健康 / 活動 / マインド / ナレッジ / WORK / 日記 / 読書・勉強 / 3A / MONTH)、`場所`(place)、`振り返り／NEXT`(**phone_number 型。設定ミスなのでテキストとして読む**)、プロスペクトと案件へのリレーション。テンプレート: 日報 / 会話ログ / 日記。

## 3. 設計との差分(移行で埋めるもの)

| 差分 | 扱い |
|---|---|
| **企業マスタが無い**(`企業名` はテキスト) | **企業レコードを新たに起こす**(01 D-00)。企業名を正規化(`name_normalized`)して名寄せし、担当者を `company_contacts` で結ぶ。同名は 1 社に寄せ、判断がつかないものは保留リストへ。企業名が空の人(友人・師匠など)は所属なしの担当者として入れる |
| **案件とプロジェクトが同居** | **分ける**(01 D-11 の要件 4・5)。`5-受注` `6-完了` は案件+プロジェクトの 2 レコードに割り、案件は受注済みとして閉じる。`1-新規` `2-案件理解/見積` は案件のみ。活動のリレーションは案件側に付ける |
| **活動が私的な記録も含む**(日記・健康・読書) | **CRM の活動だけ取り込む**(01 D-12)。タグが 日記 / 健康 / 読書・勉強 / マインド / 3A / MONTH のみ、かつプロスペクトにも案件にも紐づかないページは移行しない。判定が微妙なものは保留リストへ出して人が決める |
| `TOBE` / `メモタグ` | ラベル(`labels`)へ。担当者の属性として使われているため |
| `SF取引先ID` / `SF取引先責任者ID` | `external_ids jsonb` に退避。参照はしない |
| `最終タッチ日` / `次のアクション` | 活動から導出できるが、移行時点の値はカスタム項目に入れて残す |
| ステータスの欠番(3・4) | そのまま。`deal_stages` は現行の 4 つで作る |
| 金額が無い | `deals.amount` は移行時 NULL。以後は手で入れる |

## 4. 方針

- `scripts/import/` に移行元ごとのスクリプト。`packages/core` のコマンドを**直接**呼ぶ(`via: 'import'`)。HTTP を経由しない
- 重複ガードを効かせたまま流す。候補が出た行は作らずに一覧へ落とし、人かエージェントが判断してから再投入
- 元 ID を `custom` か `external_ref` に残す(再実行・突き合わせのため)
- 順序: Google コンタクト(識別子が揃っている)→ Notion(企業と所属)→ Todoist

## 5. 切替(J-010。スクリプト作成 J-006 とは分ける)

旧サービスを凍結するのは次の条件を全部満たしてから。満たす前は Notion・Todoist を正のまま、perfect-crm には試験的に流すだけ。

- Q-018 で決めた Todoist の必須機能が動く
- 画面 v1(J-007)で閲覧・日常のタスク操作ができる(MCP だけでは人間の閲覧手段が無い)
- 移行の件数と抜き取り照合が済んでいる
- 切戻し手順(元データを残す期間と戻し方)が書けている

手順: ①凍結日を決めて Notion・Todoist の更新を止める ②移行を流す ③照合 ④perfect-crm に切替 ⑤2 週間は元データを残し、その後アーカイブ

## 6. Todoist 置き換えの含意

- 何にも紐づかない個人タスクを許す
- v1 で持つ機能(Q-018 の回答): ラベル、日付・期限、コメント(活動)、優先度、キーボード操作、任意の軸でのカンバン、インボックス、プロジェクト/セクションへの移動。繰り返し・サブタスクは列を先に持ち、動かすのは要望が出てから
- Todoist 完了時に llm-wiki へ ingest する現在の運用(`todoist-complete` skill)は、perfect-crm の MCP で同じ流れに置き換える。エージェント側の skill を書き換えるだけで、CRM 側に機能は要らない
- Google コンタクトは同期機能を設けるが、既定では同期しない(Q-020)。CRM → Google コンタクトの一方向。有効にすると `contacts` scope が増えるので、組織設定で明示的に ON にしたときだけ要求する
