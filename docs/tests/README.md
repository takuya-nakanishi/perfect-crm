# テストケース表(領域別)

自作 CRM「Works」のテストの土台と、それに沿って起こしたケースの一覧。**設計の正は `docs/design/`**(01〜08)で、
ここは「その仕様を、誰の目線で・どの段階を・どの性質について・どの層で確かめるか」に落とした表。
表の `—` の行(まだテストが無い行)のうち L1・L2 は、無人ループ(`loops/tests/`。[`../runbook/02-loop.md`](../runbook/02-loop.md))が実装する。
**「API の資産」の列**は、同じ L2 の行を本物の HTTP API に向けて確かめる pytest で、`loops/api/` のループが埋める。

## 1. 領域と優先順位

壊れたときの損失で決めた順。表を起こす順・ループが取る順・落ちたときに直す順も同じ。

| 順 | 領域 | 表 | 覆う範囲 | 損失 |
|---|---|---|---|---|
| ① | メタデータ | [`meta.md`](meta.md) | テーブル定義・項目・ビューの作成と変更、削除と復元、定義の整合(02 §5、04 §6) | 定義が壊れると全画面が壊れる。列の値を別の型で読む事故 |
| ② | 入出力と評価 | [`io.md`](io.md) | フィルタ・並び・集計・検索の意味、日付のマクロ、CSV の読み書き、書式、richtext の洗浄、繰り返しの規則(04 §3〜§5・§7) | 画面と将来の SQL で意味が食い違う。取り込みで誤った関連付け |
| ③ | タスク | [`tasks.md`](tasks.md) | 追加欄の読み取り、完了と元に戻す、繰り返し、ラベル(02 §3、05 §3) | Todoist の代わりにならない |
| ④ | 活動 | [`activities.md`](activities.md) | 記録、時系列の合成(活動 + 言及 + 完了したタスク)、@ の言及(04 §9) | 経緯が欠ける・重複する |
| ⑤ | 台帳 | [`records.md`](records.md) | 一覧・カンバン・レポート・パネル・検索・作成・編集・削除、楽観更新、キー操作、ぱんくず(05) | 日常の操作の軽快さと正しさ |
| ⑥ | 環境設定と連携 | [`settings.md`](settings.md) | 管理者の制限、MCP のトークン、Web フォームの受け口、Google ドライブ、CSV の画面(04 §8・§10、05 §11) | 外からの書き込みの安全弁 |

## 2. 4 つの軸

1 つのケースは 4 軸の座標を 1 つずつ持つ。

| 軸 | 値 | 意味 |
|---|---|---|
| 視点 | `利用者` `管理者` `システム` `外部` | 誰にとって正しければよいか。`外部` は Web サイト・AI アプリ(MCP)・CSV の送り手 |
| 段階 | 領域ごとに表の冒頭で定義 | 業務のどの段階か |
| 性質 | `整合` `可逆` `権限` `冪等` `即時` `表記` `キー` `安全弁` `頑健性` `証跡` | 何が崩れると困るか。`可逆` = 「元に戻す」で戻る(05 §5 の設計方針。この製品では確認ダイアログの代わり)。`即時` = 楽観更新で応答を待たない。`キー` = キーボード操作と日本語入力の変換中の扱い |
| 層 | `L1` `L2` `L3` `L4` `L5` | どこで確かめるのが最も安く確実か(§3) |

### 起こすときの規則

- **否定を対にする。**「できる」を確かめたら「できない人・できない状態」(管理者でない、削除中、値が無い)を 1 つ以上
- **境界を持つ。**桁数ちょうどと +1、日付の当日と翌日、0 件、最後の 1 枚(ビュー・テーブル)
- **元に戻せるかを必ず 1 つ。**この製品は確認を挟まないので、可逆の行が安全弁になる
- **層は一番低いところに置く。**L3(実ブラウザ)で網羅しない。判定は lib かモックのエンジンに出して L1・L2 で固める
- **業務ルールは L2 で確かめる。**画面に同じ計算を持たせない設計(CLAUDE.md)なので、ルールはモックのエンジンだけにある

## 3. 層と置き場

| 層 | 何を | 置き場 | 実行 | 誰が書くか |
|---|---|---|---|---|
| L1 | `frontend/src/lib/*.ts` の純関数(フィルタの評価、日付、書式、読み取り、洗浄、下書き) | 対象の隣の `*.test.ts` | `cd frontend && npm test`(Vitest) | 無人ループ |
| L2 | モックのエンジン(`frontend/src/mocks/*.ts`)。**バックエンドができるまで、サーバの振る舞いの正**。検証・既定値・業務ルール・時系列の合成・テーブル設定の決まり・CSV・受け口 | 対象の隣の `*.test.ts` | 同上 | 無人ループ |
| L3 | 実ブラウザの画面(Playwright)。ログインから環境設定まで通しで | `frontend/e2e/smoke.mjs` の検査(`ok(…, 'ラベル')`) | `npm run e2e`(開発サーバ)、`scripts/e2e-http.sh`(本物の API + E2E 用の DB)。本番には流さない | 人と、人が起こしたセッション |
| L4 | PostgreSQL の制約・トリガ・RLS | `backend/tests/` の pytest(実物の DB に対して回る) | `cd backend && uv run pytest` | 人と、人が起こしたセッション |
| L5 | 公開 URL(Access 越し)、スマホの実機 | `scripts/cloudflare-access-check.py --exec` | 人 | 人 |

**L2 のテストは、同じケースを HTTP にも向けて流す**(04 の契約が同じなので、期待値はそのまま使える)。
バックエンドの pytest は表の「API の資産」列で追い、関数の名前を `test_<ID>_…`(例 `test_IO_001_ne_は_NULL_を含む`)にする。
埋めるのは `loops/api` のループ([`../runbook/02-loop.md`](../runbook/02-loop.md) §10)。
モックの `localStorage` は Vitest では happy-dom が持つ。テストは `resetTables()` / `resetSchema()` で毎回初期状態にする。

### テストの書き方

- 1 つの `it` が表の 1 行。**名前を ID で始める**(`it('IO-001 ne は NULL を含む', …)`)。`--check` が ID と表の対応を検査する
- 守りになっているか確かめる: 期待値や規則をわざと変えて落ちることを見てから戻す
- 見本: [`../../frontend/src/lib/filter.test.ts`](../../frontend/src/lib/filter.test.ts)

## 4. 表の読み方

| 列 | 意味 |
|---|---|
| ID | 領域の接頭辞 + 連番。**欠番を埋めない**(消えたケースの ID は再利用しない) |
| 視点・段階・性質・層 | §2 |
| ケース | 「**〈視点〉: 〈操作〉 → 〈期待〉**」 |
| 対応する資産 | 実在するテスト(Vitest・E2E)。無い行は **—**。書いたら名前をその行に入れる(行は消さない) |
| API の資産 | 同じ行を**本物の HTTP API**に向けて確かめる pytest(`backend/tests/`)。L2 の行だけが対象で、`loops/api` のループが埋める |

資産の書き方: 単体は `filter.test.ts`(ファイル名。`frontend/src/` 配下を `--check` が探す)、E2E は `smoke.mjs「ラベル」`(`ok()` の 2 つめの引数。`node scripts/loop-next.mjs --labels` で一覧できる)、部分的なら `smoke.mjs「…」(部分)` + 何が足りないかを備考に。

表と実在するテストの対応(ファイルの有無、`it` の ID、E2E のラベル)は `node scripts/loop-next.mjs --check` が検査し、`scripts/verify.sh` から回る。

## 5. 持たない検証とその条件

| 持たない | 理由 | 持つ条件 |
|---|---|---|
| 画面の部品の単体テスト(React Testing Library) | 画面はメタデータで描く薄い層で、判定は lib とモックにある。見た目はスクリーンショットで見る | 部品に判定が入り始めたとき |
| 負荷・性能 | 利用者 1〜3 名、レコード 1,000 件 | 一覧が数百件を超えたとき(04 §12 のページング) |
| L4 | DB がまだ無い | J-022 で実テーブルができたとき |
